# VAULT TRUST LAB

## 현재 구현 범위

`app/`은 TESSERA와 DIGITAL VAULT가 하나의 클라이언트 암호화 경계를 공유한다는 제품 가설을 검증하는 Trust Lab MVP다.

- Supabase Auth 기반 초대 전용 VAULT ID 로그인
- 최초 로그인 비밀번호 변경과 TOTP 인증 앱 등록
- AAL2 세션을 요구하는 데이터베이스 RLS
- AAL2 조직 관리자 전용 임시 VAULT 계정 발급
- 조직 관리자 전용 구성원 목록과 복구 가능한 로그인 정지·복구
- 관리자 자신과 다른 관리자 계정의 접근 변경 차단
- 앱을 다시 열 때 서버에서 접근 정지 상태 재확인
- 실명·실제 이메일·휴대폰 번호 미수집
- 브라우저 메모리에서 비추출 AES-GCM 키 생성
- 같은 조직의 다른 구성원 기기 공개키 조회
- 변경 가능한 별명과 변경 불가 VAULT ID를 함께 쓰는 조직 구성원 디렉터리
- VAULT ID·별명 기반 연락처 검색과 기기 미등록 상태 표시
- 한 화면에서 연락처·대화·작성기를 이해할 수 있는 메신저형 데스크톱 UI
- 모바일 연락처 목록 → 대화방 전환 흐름
- 모바일 전용 상단 앱 바와 테세라·디지털 볼트·기록·설정 하단 탭
- 디지털 볼트 모바일 추가 메뉴(텍스트·파일·사진/영상·카메라)
- 홈 화면 설치가 가능한 PWA manifest와 오프라인 앱 셸
- WebAuthn 패스키 로그인·등록 UI와 지원 여부 안내
- 같은 브라우저 탭에서 다른 계정으로 로그인했을 때 세션 충돌 감지 및 전송 차단
- ECDH P-256 + HKDF-SHA256으로 기기 간 공유키 파생
- AES-256-GCM으로 브라우저에서 1:1 메시지 암호화·복호화
- 한 논리 메시지를 상대방의 모든 활성 기기 공개키로 각각 암호화하는 다중 기기 봉투 전송
- 발신 화면에서는 기기별 암호문을 한 메시지로 묶고, 한 기기 이상이 확인하면 전달·읽음 상태를 승격
- Supabase에는 송수신 경로, IV, 암호문만 저장하고 평문은 미저장
- 대화 당사자와 TOTP AAL2 세션만 허용하는 메시지 RLS
- 다른 구성원의 기기 행을 공개하지 않고 서버 내부에서 송수신 경로를 검증하는 RLS 보조 함수
- Supabase Realtime 기반 새 암호문 수신
- 발신 메시지의 전송됨·전달됨·읽음 상태 표시
- AAL2 수신자와 활성 수신 기기만 호출할 수 있는 수신확인 RPC
- 네트워크 복구 시 최근 대화 재조회와 누락된 암호문·수신 상태 동기화
- 오프라인 중 작성 내용 유지와 전송 버튼 차단
- 최근 대화 우선 정렬, 최근 활동 시각, 안 읽은 메시지 수를 표시하는 대화 목록
- 파일별 키를 이용한 실제 파일 암호화·복호화
- 테세라 첨부파일을 상대방의 활성 기기별 키 봉투로 공유
- 파일 키 폐기 후 접근 불가 상태 시연
- 메시지 본문과 파일명을 포함하지 않는 로컬 감사 이벤트
- 메시지·파일 평문이 서버로 전송되지 않는 클라이언트 암호화 구조

이 구현은 투자자와 디자인 파트너에게 제품 원리와 Golden Path를 보여주는 기술 시연이다. 계정·별명·공개 기기 정보·메시지 암호문, 수신확인 시각, 최근 대화 시각과 안 읽은 개수는 Supabase에 유지되며, 메시지 평문과 개인 키는 브라우저 경계 밖으로 보내지 않는다. 별명은 조직 구성원에게 표시되지만 실명 입력을 요구하지 않으며, VAULT ID는 식별자로 계속 유지한다. 현재 메시지는 한 사용자가 상대방의 모든 활성 기기에 기기별 암호문을 보내는 1:1 계정 대화와 암호화 첨부파일 공유를 지원한다. 오프라인 재접속 시 최근 100개 메시지를 다시 동기화하지만 오프라인 발신 큐와 발신자의 다른 기기로 보낸 메시지를 동기화하는 기능은 아직 지원하지 않는다. Double Ratchet, 순방향 비밀성, 완성된 키 교체·폐기 전파도 아직 구현하지 않았다. 따라서 완성된 E2EE 메신저, 디지털 금고, 상용 보안 제품 또는 규제 준수 제품이 아니다.

## 실행

저장소 루트에서 정적 서버를 실행한 뒤 `/app/`에 접속한다.

```text
http://localhost:{port}/app/
```

`file://`에서도 일부 화면은 열리지만 Web Crypto와 파일 동작 검증은 로컬 HTTP 환경에서 수행한다.

## 모바일 설치와 간편 로그인

- Android Chrome/Edge에서는 브라우저의 `앱 설치` 또는 앱 설정의 `홈 화면에 설치`를 사용한다.
- iPhone Safari에서는 공유 메뉴의 `홈 화면에 추가`를 사용한다.
- 설치 후에는 전체 화면에 가까운 독립 실행형 앱으로 열리며 테세라와 디지털 볼트를 하단 탭으로 전환한다.
- 패스키는 기기의 지문·Face ID·화면 잠금으로 로그인 서명을 승인하는 방식이다. 생체정보 자체는 앱이나 서버로 전송되지 않는다.
- 실제 패스키 활성화는 고정 HTTPS 도메인과 Supabase Passkey 설정을 확정한 뒤 수행한다. 그전에는 기존 VAULT ID·비밀번호·TOTP 로그인을 유지한다.
- 패스키가 활성화된 뒤에도 계정 발급, 복구, 키 폐기 같은 민감 작업은 현재의 TOTP AAL2를 유지한다.

## Mobile Friendly V2 실험

`codex/mobile-friendly-v2` 브랜치는 현재 보안 기술 시연 구조를 보존하면서 일상적인 모바일 서비스 사용성을 검증한다.

- 디지털 볼트 첫 화면을 파일 업로드가 아니라 `패스워드`, `내면 일기`, `잠긴 추억`, `파일 보관`의 목적 중심 구조로 변경
- 패스워드 생성, 암호화 보관, 앱 내부 복호화 열기와 클립보드 복사 흐름 제공
- 내면 일기의 제목·본문·작성 시각을 하나의 암호화 항목으로 보관하고 앱에서 다시 읽기
- 잠긴 추억에는 공유 동작을 제공하지 않으며 접근키 폐기 전에 복구 불가 경고 표시
- 모든 생활형 항목은 별도 평문 테이블을 만들지 않고 기존 파일별 AES-GCM 암호화와 기기 키 봉투 구조를 재사용

`잠긴 추억`은 법적·윤리적으로 삭제 자체를 금지하는 기능이 아니다. 사용자의 삭제권은 유지하면서 공유 경로를 제거하고 우발적 접근키 폐기를 막는 보호 UX다. 상용화 전에는 복구 유예기간과 재인증 정책을 서버에 추가해야 한다.

- 메시지 페이지네이션과 오프라인 발신 큐
- 기기 키 교체·폐기와 과거 메시지 접근 정책

- 3~10명 소규모 그룹
- 기기 간 세션 및 키 복구
- 대용량 첨부파일의 스트리밍 암호화와 전송 재시도

### 3. Archive Spike

- 대용량 스트리밍 파일 암호화

### 4. Control Plane

- Supabase Auth·Postgres·Storage 기술 검증

- 모든 공개 테이블의 RLS

- 서비스 역할 키의 서버 전용 관리

### 5. Security Gate

- 위협 모델 확정
- 서버·로그·백업 평문 미저장 자동 검사
- 키 분실·기기 분실·멤버 퇴장 시나리오
- 외부 암호 구현 검토 범위 확정
- 외부 검토 전 보안 인증 및 절대 보안 표현 금지

- `notifications.js`: 사용자 선택에 의한 알림 구독/해제, 기기·계정 바인딩, 테세라 탭 숫자와 지원 OS 배지.

- 실제 푸시는 Supabase DB·Edge Function·전용 비밀키·스케줄러 활성화가 모두 필요. 프론트 파일만 배포해도 푸시가 자동으로 켜지는 것은 아님.
- 운영 Supabase에 알림 DB·비밀키·`tessera-push` 함수·즉시 호출/1분 재시도 스케줄러 등록 완료. 서버 인증 정상 호출 200, 미인증 호출 401 확인.

- 비공개 백엔드 설정 절차는 로컬 `supabase/push-README.md` 참고. 이 폴더는 기존 정책대로 공개 Git에서 제외됨.
